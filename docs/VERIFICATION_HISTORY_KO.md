# 검증 이력

지난 검증 실행, 매트릭스 밖에서 한 일회성 실측, 그 실행들 때문에 바꾼 검증
하네스를 손으로 정리한 기록입니다. 현재 결과와 그 결과가 다루는 범위는 최신 전체
실행으로 생성한 [검증 결과](VERIFICATION_KO.md)에 있습니다. 매트릭스가 어떻게
동작하고 어떻게 실행하는지는 [검증 범위](ARCHITECTURE_KO.md#검증-범위)에 있습니다.

`.verify-runs/`로 시작하는 경로는 관리자 컴퓨터에 있는 실행 기록을 가리킵니다. 이
디렉터리는 gitignore 대상이라 저장소에는 들어 있지 않습니다.

아래에서 쓰는 용어는 다음과 같습니다.

- **슬롯**: 모델 하나가 시나리오 하나를 실행하는 단위입니다. 6개 모델 매트릭스는
  66개 슬롯입니다.
- **전체 실행과 부분 실행**: 전체 실행은 모든 슬롯을 돌립니다. 부분 실행은 고른
  슬롯만 돌리며, 전체 결과에 포함하지 않습니다.
- **코드 지문**: `src/`, `scripts/verify/`, `bin/`과 루트 패키지 파일에 있는 구현
  파일에 대한 SHA-256 해시입니다. 범위 이름은 `verification-code-v1`입니다. 실행마다
  시작과 끝에 기록합니다.
- **통과**: 전체 실행은 모든 슬롯이 통과하고, `~/.claude/settings.json`이 바뀌지
  않았고, 커밋과 코드 지문이 모두 시작과 끝에서 같을 때만 통과입니다.
- `blocked`(실행 불가)는 슬롯을 판정할 수 없었다는 뜻입니다. 예를 들어 시간이
  초과됐거나, 브리지가 죽었거나, `tool_use`에 짝이 되는 `tool_result`가 없었던
  경우입니다. 통과하지 않은 것으로 셉니다.

## 최신 전체 실행

실행 `2026-09-23T09-11-26-241Z`는 2026-09-23(KST)에 커밋 `bed30ce`, Claude Code
2.1.280으로 6개 모델 × 11개 시나리오를 돌려 66개 슬롯을 모두 통과했습니다. 479초(7분
59초)가 걸렸습니다. `--timeout-scale 2`, 모델 작업자 3개 × 시나리오 작업자 2개,
`PENDING_TOOL_WAIT_MS=30000`으로 실행했습니다. 이 대기 시간의 브리지 기본값은
10000입니다. 검증 하네스는 자기 환경 변수를 슬롯마다 띄우는 브리지에 넘기므로
30000이 적용됐습니다. 이 값들은 기본값이 아닙니다. 옵션 없이 `npm run verify`를
실행하면 모델 작업자 6개 × 시나리오 작업자 2개, 타임아웃 배율 1, 대기 시간
10000 ms를 씁니다. 모델 작업자를 3개로 줄인 이유는 앞선 7 × 2 실행에서 네이티브
백그라운드 작업 프로세스가 시작 단계에서 멈췄기 때문입니다. 작업자가 적을수록 시작 부하가
줄어듭니다. 기본값으로 돌린 유일한 6개 모델 전체 실행
`2026-09-23T07-29-33-556Z`는 통과하지 못했습니다.

### 모델 목록과 1M 컨텍스트 창

- **확인한 것:** Claude Code가 보여 주는 `/model` 목록의 행과, 행마다 Claude Code가
  가정하는 컨텍스트 창.
- **실행 시각:** 2026-09-23 09:32 UTC, 최신 전체 실행 뒤.
- **결과:** Claude Code의 `supportedModels()`는 `Default`와 6개 행만 순서대로
  반환했습니다. `setModel()`로 각 행으로 바꿀 때 브리지에 요청이 가지 않았습니다.
  `getContextUsage()`는 Opus 5.5, Sonnet 5, GPT-6 세 행에서 1M(자동 압축 967K),
  Haiku 4.5에서 200K(자동 압축 167K)를 보고했습니다. `Default`와 `opus`·`sonnet`
  별칭은 `claude-opus-5-5[1m]`과 `claude-sonnet-5[1m]`(1M)으로 해석됐습니다.
- **직접 입력한 모델 ID:** 목록 밖에서 입력한 ID는 요청 한 번으로 확인합니다.
  Opus 4.8과 4.7은 1M으로 확인됐습니다. Opus 5는 모델이 답하기 전에 Claude Code가
  5초 만에 확인을 포기했습니다. 앞선 측정에서는 확인됐습니다.
- **기록:** `.verify-runs/picker-1m-2026-09-23T09-32-55Z/`

### 런타임 MCP 서버

- **확인한 것:** Copilot 런타임이 사용자의 Copilot 설정에 있는 MCP 서버를 여전히
  띄우는지, 그리고 그 비용.
- **변경 전후 비교(`1df3aa4`):** 새로 띄운 브리지가 Claude Haiku 4.5로 Claude 세션
  두 개를 동시에 처리하게 하고, 이를 네 쌍 번갈아 돌렸습니다. 변경 전에는 열린 세션

  `microsoft-learn`·`github-mcp-server`에 연결했습니다. 런타임은 SDK 세션이 닫힐

### 업스트림 429, 503과 retry-after

- **확인한 것:** Copilot의 추론 엔드포인트가 실패할 때 Claude Code가 받는 응답.
  Copilot 런타임의 `COPILOT_API_URL`을, 추론 요청을 429나 503으로 실패시키는 로컬
  프록시로 지정했습니다. 모델은 Claude Haiku 4.5, `-p` 모드입니다.
- **실행 환경:** Claude Code 2.1.281과 지금 `9f1649a`에 들어 있는 브리지 수정.
- **결과:** 런타임이 6번 시도했습니다(429는 약 50초, 503은 약 17초). 이어서 브리지가
  429 `rate_limit_error`와 529 `overloaded_error`를 반환했습니다. Claude Code는 약
  0.5초 뒤 한 번 재시도해 성공했습니다. 여기에는 브리지 수정이 필요했습니다. 런타임은
  `session.error`를 보고하기 전에 턴을 끝내는데, 이전 브리지는 그 턴을 빈 성공으로
  마무리했기 때문입니다.
- **`retry-after` 처리:** 프록시가 90초 `retry-after`를 보냈을 때 런타임은 스스로
  기다렸고, 약 95초 동안 이벤트가 없었습니다.

`npm run verify`는 업스트림 오류를 주입하지 않습니다. `BRIDGE_TEST_FAULTS`는
`npm test`에서만 씁니다. 따라서 이 실측이 429/529 변환의 유일한 실제 근거입니다.
변환 규칙은 [업스트림 오류](ARCHITECTURE_KO.md#업스트림-오류)에 있습니다.
